1. EXECUTIVE SUMMARY & FEATURE OBJECTIVES
================================================================================
US-22 establishes rigorous controls over external LLM consumption across the
AI/ML service, ensuring deterministic rules-first execution, strict budget
governance, privacy compliance, and duplicate-request suppression.

Primary Acceptance Criteria & NFRs:
- NFR5.1: Rule-based AST and regex checks execute first, providing immediate
  static feedback without incurring AI latency or token cost.
- NFR5.2: Normalized code caching using 64-character SHA-256 hexadecimal digests
  across all 5 supported languages (Python, C++, C, Java, JavaScript).
  Formatting/comment changes yield identical cache keys (cache hit, $0 cost).
  Semantic changes produce distinct cache keys (cache miss).
- NFR5.3: Configurable per-room hourly rate limiting (default 20 calls/hour)
  enforced on a rolling 60-minute window. Requests exceeding the limit return
  HTTP 200 with ai_step.status = "skipped" and error_code = "ROOM_RATE_LIMITED".
- NFR8.2: Zero user source code, compiler diagnostics, or raw error text is
  ever stored in cache keys, telemetry counters, or application logs. Only
  pure SHA-256 hashes are used.
- US-17 & FR12.2: Mandatory user consent gate.
- FR35: Mandatory Host AI switch gate.
- US-56 & FR32: Explicit room lifecycle cleanup (DELETE /v1/rooms/{id}/state)
  purging room-scoped cache entries, counters, and rate limits.

2. MANDATORY AI CONTROL PIPELINE ARCHITECTURE
================================================================================
Every AI-assisted endpoint (/v1/explain, /v1/analyses/complexity, and
/v1/analyses/crash-explanation) strictly follows this deterministic 5-step
order of operations:

  [Request Ingestion]
          │
          ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 1: Rule-Based Static Analysis (Always Runs First)      │
  │ Deterministic AST and pattern checkers detect issues.       │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 2: Consent Check (US-17, FR12.2)                       │
  │ If consent != True: Skip AI, error_code = "CONSENT_MISSING" │
  └──────────────────────────────┬──────────────────────────────┘
                                 │ Pass
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 3: Host AI Switch Check (FR35)                         │
  │ If ai_enabled != True: Skip AI, error_code = "AI_DISABLED"  │
  └──────────────────────────────┬──────────────────────────────┘
                                 │ Pass
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 4: Normalized Code Cache Check (NFR5.2, Decision 11)   │
  │ Compute 64-char SHA-256 key over normalized code.           │
  │ CACHE HIT: Return cached fix immediately.                   │
  │ * Does NOT consume room quota ($0 cost, 0 calls recorded).  │
  └──────────────────────────────┬──────────────────────────────┘
                                 │ Cache Miss
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 5: Atomic Room Rate Limit Reservation (NFR5.3, US-22)  │
  │ Atomically check quota & record call under single lock.     │
  │ If quota exceeded: Skip AI, error_code = "ROOM_RATE_LIMITED"│
  └──────────────────────────────┬──────────────────────────────┘
                                 │ Slot Reserved
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ Step 6: Outbound AI Call & Cache Population                 │
  │ Invoke LLM API, write result to cache, return response.     │
  └─────────────────────────────────────────────────────────────┘

3.1 Code Normalization & Caching (ai-ml-service/app/cache.py)
--------------------------------------------------------------------------------
Key Functions:
- `_scan_c_style_lexemes(code: str, is_js: bool = False, language: str = "cpp") -> list[tuple[bool, str]]`:
  Single-pass character scanner separating literals verbatim `(True, content)`
  from normal code `(False, content)`.
  Preserves:
  * C++ raw strings: `R"delim(...)delim"` (and prefixes `u8R`, `uR`, `UR`, `LR`)
  * Java text blocks: `"""..."""`
  * JavaScript regex literals: `/[//]/`, `/[/*]/`, `/pattern/flags` in expression context
  * Double- and single-quoted strings: `"..."`, `'...'`
  * JavaScript template literals: `` `...` ``
  * Line comments (`//...\n`) stripped while preserving significant line breaks.
  * Block comments (`/*...*/`) replaced with space (or `\n` in JS for ASI).

- `_normalize_c_style(code: str, language: str = "cpp") -> str`:
  Normalizes C, C++, and Java code.
  * Preprocessor handling: Preserves significant newlines between `#` directives
    and ordinary code. Directives ending with continuation backslashes (`\\\n`)
    are folded and normalized.
  * Operator token preservation: Tokenizes multi-character operators (`++`,
    `--`, `+=`, `==`, `<<`, `>>`, `&&`, etc.) and single-character operators
    (`+`, `-`, `*`, `&`, etc.) using maximal munch.
  * Spacing: Retains necessary whitespace between adjacent operators (`+ ++`,
    `++ +`, `+ +`, `- --`, `* ++`, `& &`, `< <`, `> >`, `= =`) so separate
    operators never merge, while removing whitespace around structural
    punctuation (`;`, `,`, `(`, `)`, `[`, `]`, `{`, `}`).

- `_normalize_javascript(code: str) -> str`:
  Normalizes JavaScript code with full Automatic Semicolon Insertion (ASI)
  awareness. Preserves semantic line breaks after restricted keywords (`return`,
  `throw`, `break`, `continue`, `yield`) and before postfix `++`/`--`.
  Treats regular-expression literals as verbatim tokens.

- `_normalize_python(code: str) -> str`:
  Uses Python's standard-library `tokenize` module. Preserves semantic indentation
  (INDENT/DEDENT), multiline docstrings, and string literals while stripping
  comments (`tokenize.COMMENT`) and non-semantic whitespace.

- `compute_cache_key(code: str, language: str, request_type: str = "complexity", error_output: str = "", error_signature: str = "") -> str`:
  Generates a 64-character lowercase SHA-256 hexadecimal hash over:
  `normalized_code:language:request_type:error_signature:error_output`
  Guarantees that both `error_signature` (e.g. `heap-buffer-overflow:14`) and
  `error_output` (raw sanitizer output) participate in the hash.

- `AnalysisCache`:
  Thread-safe in-memory cache keyed by `(room_id, sha256_hash)`. Includes LRU
  eviction, room-scoped key tracking, and `clear_room(room_id)` for US-56 room
  cleanup. Never stores or logs raw user code.

--------------------------------------------------------------------------------
3.2 Atomic Sliding-Window Rate Limiter (ai-ml-service/app/limiter.py)
--------------------------------------------------------------------------------
Class: `RoomRateLimiter`:
- `check_and_reserve(room_id: Optional[str], limit: Optional[int] = None, now: Optional[float] = None) -> bool`:
  ATOMIC operation executing quota check and call recording inside a single
  critical section protected by `threading.Lock()`.
  1. Acquires lock.
  2. Prunes timestamps older than 3600 seconds (`_cleanup_unlocked`).
  3. If active calls >= limit: releases lock and returns `False` (rate limited).
  4. Appends current timestamp to room list, releases lock, and returns `True`
     (quota slot reserved).
- `is_rate_limited(room_id, limit, now) -> bool`: Non-mutating quota status query.
- `record_call(room_id, now) -> None`: Explicit timestamp recording.
- `get_count(room_id, now) -> int`: Active window call count.
- `clear_room(room_id) -> None`: Purges all timestamps for the given room (US-56).
- `clear() -> None`: Full reset.

--------------------------------------------------------------------------------
3.3 Rules-First Orchestrator (ai-ml-service/app/rules/patterns.py)
--------------------------------------------------------------------------------
Function: `run_rule_based_analysis_with_ai_fallback(...)`:
- Runs `detect_slow_patterns` AST & regex rules.
- Check 1: User consent missing/false -> returns skipped `CONSENT_MISSING`.
- Check 2: Host AI switch disabled/missing -> returns skipped `AI_DISABLED`.
- Check 3: Normalized code cache hit -> returns cached suggestion immediately
  without consuming room rate-limit quota.
- Check 4: Outbound call rate limit -> invokes `check_and_reserve(room_id)`.
  If False, returns skipped `ROOM_RATE_LIMITED`.
- Check 5: Quota reserved -> executes `ai_fallback()`, writes suggestion to
  cache, and returns status "ok".

--------------------------------------------------------------------------------
- `POST /v1/explain` (explain.py):
  Conforms to T-18 v2 contract. Gated through `run_rule_based_analysis_with_ai_fallback`.

- `DELETE /v1/rooms/{room_id}/state` (analyses.py):

4.1 Issue 1: Preserve C/C++ Preprocessor Directive Boundaries
--------------------------------------------------------------------------------
Review Finding:
`sub = re.sub(r"\s+", " ", part)` collapsed newlines between preprocessor
directives and following code. Consequently, `#define X 1\nX` and `#define X 1 X`
normalized to the same string (`#define X 1 X`).

Fix Implemented:
1. `_normalize_c_style` splits non-literal code into lines.
2. Directives starting with `#` are processed on their own line.
3. Significant newlines separating preprocessor directives from subsequent code
   or directives are strictly preserved (`#define X 1\nX` vs `#define X 1 X`).
4. Continuation lines (`\\\s*\n`) within directives are folded into single
   spaces, so continuation indentation differences normalize identically.

Regression Test Added:
`test_c_cpp_preprocessor_boundaries_preserved()` in `test_cache_rate_limit.py`:
- Asserts `compute_cache_key("#define X 1\nX", "cpp") != compute_cache_key("#define X 1 X", "cpp")`.
- Asserts continuation `#define X \\\n 1\nX` produces identical key to `#define X 1\nX`.
- Asserts multiple `#include` statements remain on separate lines.

--------------------------------------------------------------------------------
4.2 Issue 2: Preserve C/C++ Operator Token Boundaries
--------------------------------------------------------------------------------
Review Finding:
`sub = re.sub(r"\s*([=+\-*/<>!&|]+)\s*", r" \1 ", sub)` collapsed adjacent
operators into identical sequences, altering program meaning (e.g., `a + ++b`
vs `a++ + b`).

Fix Implemented:
1. Replaced generic regex with maximal munch tokenization (`_C_TOKEN_RE`)
   distinguishing multi-char operators (`++`, `--`, `+=`, `==`, `<<`, `>>`,
   `&&`, `||`, etc.) from single-char operators (`+`, `-`, `*`, `&`, etc.).
2. In `_normalize_c_tokens`, whenever two operator tokens are adjacent in the
   stream, a space is explicitly inserted between them:
   `a + ++b` -> `'a + ++ b'`
   `a++ + b` -> `'a ++ + b'`
   `a + +b`  -> `'a + + b'`
   `* ++p`   -> `'* ++ p'`
   `& &x`    -> `'& & x'` vs `&& x` -> `'&& x'`
   `a < < b` -> `'a < < b'` vs `a << b` -> `'a << b'`

Regression Test Added:
`test_c_cpp_operator_token_boundaries_preserved()` in `test_cache_rate_limit.py`:
- Verifies distinct keys for `a + ++b`, `a++ + b`, `a + +b`, and `a++ + ++b`.
- Verifies distinct keys for `a - --b` and `a-- - b`.
- Verifies distinct keys for `& &x` and `&& x`, `a < < b` and `a << b`.
- Verifies formatting variations (`a + ++b` vs `a   +   ++  b`) yield identical keys.

--------------------------------------------------------------------------------
4.3 Issue 3: Comment Removal Aware of All Supported Language Literals
--------------------------------------------------------------------------------
Review Finding:
The comment scanner stripped comment markers without recognizing C++ raw strings
`R"(...)"`, Java text blocks `"""..."""`, and JavaScript regex literals `/[//]/`.

Fix Implemented:
1. Implemented `_scan_c_style_lexemes` character scanner:
   - C++ raw strings: recognizes `R"delim(...)delim"` (and prefixes `u8R`, `uR`,
     `UR`, `LR`). Delimiter is parsed up to `(`, and all content is preserved
     verbatim until `)delim"`.
   - Java text blocks: recognizes `"""..."""`, preserving all internal content
     and line breaks verbatim.
   - JavaScript regex literals: in expression context, recognizes `/pattern/flags`
     including character classes `[...]` containing `//` or `/*`.
2. `_strip_comments_c_style` joins lexemes, guaranteeing zero comment removal
   inside any of these literal constructs.

Regression Test Added:
`test_comment_removal_aware_of_raw_strings_text_blocks_and_regex()`:
- Verifies comment markers inside `R"(// not a comment /* nor this */)"` are kept.
- Verifies modifying comment-like text inside raw strings, text blocks, or regex
  changes the cache key.
- Verifies formatting code outside the literal produces identical cache keys.

--------------------------------------------------------------------------------
4.4 Issue 4: Include Actual Sanitizer Output in Crash Explanation Cache Keys
--------------------------------------------------------------------------------
Review Finding:
`err = (error_signature or error_output or "").strip()` caused `error_output`
to be ignored whenever `error_signature` was supplied. Consequently, two
different sanitizer outputs with the same error type and line number produced
the exact same cache key.

Fix Implemented:
1. Updated `compute_cache_key` in `app/cache.py` to hash both:
   `hasher.update((error_signature or "").strip().encode("utf-8"))`
   `hasher.update(b":")`
   `hasher.update((error_output or "").strip().encode("utf-8"))`
2. In `app/routers/analyses.py`, `explain_crash` passes both
   `error_signature=f"{error_type}:{line_number}"` and
   `error_output=payload.sanitizer_output`.

Regression Test Added:
`test_sanitizer_output_differentiates_crash_explanation_cache_key()`:
- Two crash requests with identical `error_type="heap-buffer-overflow"` and
  `line=14` but different sanitizer outputs (Read at 0x602000000010 vs Write at
  0x602000000050) produce different cache keys.
- Sending both to `/v1/analyses/crash-explanation` triggers 2 distinct LLM calls.

--------------------------------------------------------------------------------
4.5 Issue 5: Make Room Rate-Limit Checking and Recording Atomic
--------------------------------------------------------------------------------
Review Finding:
`is_rate_limited()` and `record_call()` were called separately in both
`patterns.py` and `analyses.py`. Under concurrent requests, multiple callers
could pass the check before any recorded its call, exceeding the room limit.

Fix Implemented:
1. Created `check_and_reserve(room_id, limit, now) -> bool` on `RoomRateLimiter`
   in `app/limiter.py`. Performs sliding-window cleanup, quota check, and timestamp
   append inside a single `with self._lock:` block.
2. In `app/rules/patterns.py` (`run_rule_based_analysis_with_ai_fallback`),
   replaced separate check/record calls with:
   `elif room_id and not get_room_rate_limiter().check_and_reserve(room_id):`
3. In `app/routers/analyses.py` (`explain_crash`), replaced separate check/record
   calls with `check_and_reserve(payload.room_id)`.

Regression Tests Added:
- `test_atomic_rate_limiter_check_and_reserve_concurrency()`: 50 concurrent
  threads competing for 5 quota slots; exactly 5 succeed and 45 are rejected.
- `test_endpoint_concurrency_at_quota_boundary()`: 12 concurrent requests to
  `/v1/analyses/complexity` at quota=3; exactly 3 succeed with `ai_step.status="ok"`
  and 9 return HTTP 200 with `ai_step.status="skipped"` and `error_code="ROOM_RATE_LIMITED"`.

4.6 Secondary Review Resolutions (Issues A–D)
--------------------------------------------------------------------------------
Following the resolution of Chandan's five primary review comments, a secondary
in-depth automated review identified four additional areas for refinement:

--- Issue A: JavaScript Regex Detection in Control-Flow & Statement Contexts ---
Review Finding:
The lexer scanner previously identified regex literals only after unary/binary
operators or statement delimiters, missing control-flow closing parentheses:
    `if (condition) /[//]/.test(value);`
After `)`, the scanner did not permit `/` as a regex start, erroneously treating
the character class `[//]` as a line comment.

Fix Implemented:
1. Implemented a paren nesting stack (`paren_stack`) in `_scan_c_style_lexemes`
   specifically tracking opening parentheses attached to control keywords
   (`if`, `while`, `for`, `with`).
2. When closing `)` matches a control structure, `last_closed_paren_was_control`
   is flagged `True`, allowing the immediately following `/` to be parsed as a
   regex literal.
3. Conversely, expression parentheses (e.g. `(a + b) / 2`) maintain standard
   division precedence without misinterpreting `/` as a regex start.
4. Added support for statement-start contexts and additional JavaScript keywords
   (`do`, `else`).

Regression Tests Added:
- Verified that `if (condition) /[//]/.test(value);` preserves the `//` sequence
  and changes in the regex content produce distinct cache keys.
- Verified that `while`, `for`, and statement-start regexes are correctly parsed.
- Verified that JavaScript arithmetic division (`(a + b) / 2;`, `x / 2;`, `arr[0] / 2;`)
  is never misidentified as regex literals.

--- Issue B: C++ String and Character Literal Encoding Prefixes ---
Review Finding:
In C++, encoding prefixes such as `u8`, `u`, `U`, and `L` (e.g. `u8"hello"`,
`L"wide"`, `u'x'`) define distinct literal semantics compared to an identifier
followed by an unprefixed string (e.g. `u8 "hello"`). The lexer previously
tokenized the prefix as an identifier and the string as a literal, and
normalization inserted a space between them.

Fix Implemented:
1. Enhanced `_scan_c_style_lexemes` to detect C++ encoding prefixes (`u8`, `u`,
   `U`, `L`) immediately preceding double (`"`) or single (`'`) quotes.
2. Encapsulates the entire prefixed construct as a single atomic literal token
   `(True, 'u8"hello"')`.
3. Updated `_normalize_c_tokens` to respect prefixed literals without splitting
   or inserting intra-token whitespace.

Regression Tests Added:
`test_c_cpp_prefixed_string_and_char_literals_preserved()`:
- `u8"hello"` vs `u8 "hello"` produce distinct SHA-256 cache keys.
- `L"wide"` vs `L "wide"` produce distinct SHA-256 cache keys.
- UTF-16 (`u"..."`) and UTF-32 (`U"..."`) produce distinct SHA-256 cache keys.
- Character literal prefixes (`u8'a'`, `u'a'`, `U'a'`, `L'a'`) produce distinct keys.
- Whitespace formatting variations around prefixed literals preserve identical keys.

--- Issue C: Python Documentation Alignment ---
Review Finding:
`ai-ml-service/README.md` stated that standalone docstrings were removed,
contradicting the current AST/token-based implementation that preserves docstrings.

Fix Implemented:
Updated `ai-ml-service/README.md` to accurately document that Python docstrings,
string literals, and semantic indentation are preserved, while only comments and
redundant blank lines are normalized.

--- Issue D: Process-Local Atomic Rate Limiter Deployment Architecture ---
Review Finding:
The reviewer noted that `RoomRateLimiter` uses in-memory sliding windows with
`threading.Lock()`, which enforces concurrency within a single Python process
(multi-threaded Uvicorn), but would not share counters across multiple detached
processes/replicas.

Architectural Clarification & Deployment Contract:
1. Current Deployment Model:
   The AI/ML service is deployed as a single-process FastAPI container with
   room-affinity (sticky sessions) at the ingress layer. Within this deployment
   boundary, the atomic `check_and_reserve()` lock provides 100% thread-safe
   quota enforcement under high concurrency.
2. Extensibility Contract:
   The `RoomRateLimiter.check_and_reserve(room_id, limit, now)` API was designed
   as an atomic reservation abstraction. For multi-replica horizontal clustering
   without sticky routing, the in-memory dictionary is designed to be replaced by
   a Redis sorted-set Lua script with the identical method signature, requiring zero
   modifications to callers (`patterns.py`, `analyses.py`).
