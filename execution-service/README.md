# execution-service

Spring Boot service that runs user code in isolated Docker containers.

- **Port:** `8082` (T-06 section 1)
- **Health:** `GET /actuator/health`
- **Run:** `POST /v1/runs` — see [docs/api-contracts.md](../docs/api-contracts.md) sections 4, V2.8 (Decision 8) & V2.9 (Decision 9)

> **Sprint 2 / T-19 status (Jay Limbasiya & Yash Oza):**
> The run endpoint consumes the unified **RunSpec** object (Decision 8) and returns
> enriched execution results with Decision 9 fields (`runner`, `ran_at`, `visibility`,
> `saved_versions`, `failure`, `compile_time_ms`).
> Runs code through **DockerRunner** (US-09, PR #40) by default. **FakeCodeRunner** is a deterministic in-process stub that is used only when the `stub-runner` Spring profile is active.
> Gated by **RunQueueGate** (US-11) for concurrency limiting.

## Run endpoint

```
POST http://localhost:8082/v1/runs
Content-Type: application/json
```

### Request fields (T-17 V2.8 / Decision 8)

| Field        | Type          | Required | Notes                                                                   |
|--------------|---------------|----------|-------------------------------------------------------------------------|
| `request_id` | string (UUID) | Yes      | Generated by the client (UUID v4); echoed in the response.              |
| `room_id`    | string        | Yes      | Room the result is broadcast to (FR4.5).                                |
| `session_id` | string (UUID) | Yes      | Stable browser session id (UUID v4, T-06 §3.3).                         |
| `language`   | string        | Yes      | One of: `cpp`, `python`, `c`, `java`, `javascript`                      |
| `stdin`      | string        | No       | Standard input; defaults to `""` (FR4.1).                               |
| `source`     | object        | Yes      | Spec object defining files or saved snapshot to execute (Decision 8).   |

> **Legacy field:** A body containing `code` is rejected with HTTP `422 INVALID_REQUEST`.

### Three source shapes

1. **Pair mode (inline source):**
   ```json
   {
     "kind": "inline",
     "files": [
       { "name": "main.py", "content": "print(\"hello\")" }
     ],
     "entry": "main.py"
   }
   ```
2. **Open mode (one runnable module):**
   ```json
   {
     "kind": "saved",
     "target": "module",
     "module_id": "mod_9Qx7mBvA2nR0"
   }
   ```
3. **Open mode (through entry file):**
   ```json
   {
     "kind": "saved",
     "target": "entry",
     "module_ids": "all"
   }
   ```
   *(or `"module_ids": ["mod_1", "mod_2"]`)*

### Response fields (T-17 V2.9 / Decision 9)

All fields are always present — including on compile errors, timeouts and OOM (FR4.2).

| Field               | Type                  | Notes                                                              |
|---------------------|-----------------------|--------------------------------------------------------------------|
| `request_id`        | string                | Echoed from the request.                                           |
| `room_id`           | string                | Echoed from the request.                                           |
| `language`          | string                | Echoed from the request.                                           |
| `stdout`            | string                | Always present, may be `""`.                                       |
| `stderr`            | string                | Always present, may be `""`.                                       |
| `exit_code`         | integer               | Process exit code (FR4.4).                                         |
| `execution_time_ms` | number                | Wall-clock milliseconds for the run stage only (FR4.3, FR6).        |
| `peak_memory_mb`    | number                | Peak memory in MB (FR4.3, FR6).                                    |
| `timed_out`         | boolean               | `true` if killed by wall-time limit (NFR4.1).                      |
| `oom_killed`        | boolean               | `true` if killed by memory limit (NFR4.2).                         |
| `failure_kind`      | string / null         | `"compile_error"`, `"non_zero_exit"`, `"timeout"`, or `null`. An OOM kill is always `"non_zero_exit"` with `oom_killed: true` (never `"oom"`). |
| `output_truncated`  | boolean               | `true` if output was cut at the cap (NFR4.4) or 4 MiB frame limit. |
| `message`           | string / null         | Short UI sentence, e.g. `"Time limit exceeded"`. `null` otherwise. |
| `compile_time_ms`   | number / null         | Compile stage time in ms; `null` for languages without compile stage. |
| `runner`            | object                | `{ "member_id": "...", "display_name": "..." }` (Decision 9).      |
| `ran_at`            | string (ISO-8601 UTC) | Timestamp when execution started (`uuuu-MM-dd'T'HH:mm:ss.SSS'Z'`). |
| `visibility`        | string                | `"room"` in Pair mode; `"private"` in Open mode (Decision 10).     |
| `saved_versions`    | array of objects      | Open mode: list of `{ module_id, name, version, saved_by, saved_at }`. `[]` in Pair mode. |
| `failure`           | object / null         | Open mode: `{ module_id, name, owner, last_saved_by }` if failed and pinned to a module; `null` otherwise. |

### Room delivery & audience (FR4.5, T-06 §5, Decision 10)

After execution finishes, execution-service broadcasts the run result to sync-service:
- In **Pair mode**, broadcast with audience `{"kind":"room"}`.
- In **Open mode**, broadcast with targeted session audience `{"kind":"sessions","session_ids":[sessionId]}` (visibility `private`).

## ⚠️ StubPermissionLookupService

`StubPermissionLookupService` is an in-memory stub activated by the
`stub-permissions` Spring profile (enabled by default in `application.yml`).
It returns `can_run: true` for every session that is not one of the
well-known test session IDs (`OBSERVER_SESSION_ID`, `REVOKED_SESSION_ID`,
`HOST_ONLY_SESSION_ID`, `NOT_IN_ROOM_SESSION_ID`).

**This stub must be replaced** when sync-service implements real session
lookup (T-20). To disable it, remove `stub-permissions` from
`spring.profiles.active` and register a production `PermissionLookupService`
bean.

## Prerequisites

- Java 21 (Temurin recommended)
- Maven 3.9+ or use the Maven Wrapper (`./mvnw` or `mvnw.cmd`)
- Docker Engine with the Docker CLI available in `PATH`
- A running Docker daemon

The execution service uses the Docker daemon of the machine on which it runs. Docker 29.8.2 (CLI and Engine) was used to verify this setup. The project does not currently specify a minimum Docker version.

## How to run locally

### 1. Build the runtime image

From the repository root, build the Python runtime image using the Dockerfile maintained in this repository:

```bash
docker build -t collab-sandbox-python:0.1.0 execution-service/runtime-images/python
```

The execution service expects this image tag when running Python code. Build the image again whenever its Dockerfile changes.

### 2. Run the execution service

Make sure Docker is running and the Docker CLI is available to the service.

```bash
cd execution-service

# Run all tests
mvnw.cmd test               # Windows
./mvnw test                 # Linux / macOS

# Start the service (port 8082)
mvnw.cmd spring-boot:run    # Windows
./mvnw spring-boot:run      # Linux / macOS
```

### Execution boundary

Submitted code is executed only inside temporary Docker containers started by `DockerRunner` through the machine's Docker daemon. User code must never be executed directly on the host, including during local development or tests.

`FakeCodeRunner` is a deterministic stub for controlled development and tests; it does not execute submitted code. It is selected only when the `stub-runner` profile is explicitly enabled.

The project does not use hosted code-execution services such as Judge0 or Piston. Runtime images are built from Dockerfiles maintained under `execution-service/runtime-images/`.

## Queue gate (FR16, US-11)

When the run queue is full the service refuses the new request immediately --
no container is started, no existing run is disturbed.

### How it works

Every public run request (`POST /v1/runs`) calls the **one** `RunQueueGate`. The gate
holds a semaphore whose size is `app.execution.limits.max-queue-length`. When all
permits are in use the gate throws `QueueFullException` before invoking the
code runner. `QueueFullExceptionHandler` maps that to an HTTP 503 response.

Queue health and observable in-flight state (`in_flight`, `max_queue_length`,
`retry_after_seconds`) are exposed via Spring Boot Actuator at `GET /actuator/health`
(`QueueHealthIndicator`) for monitoring and deterministic test coordination.
The details are hidden by default (`management.endpoint.health.show-details: never`).
`docker-compose.yml` keeps them hidden too (default `never`). Only the integration harness
(`tests/integration/up.sh` and the CI `integration` job) sets `MANAGEMENT_HEALTH_SHOW_DETAILS=always`;
do not enable it in production.

> **Note on API scope:** Testing in this PR covers the public endpoint `POST /v1/runs`,
> verifying that repeated public calls count toward the same queue limit and receive
> the 503 `QUEUE_FULL` refusal. The future internal endpoint `POST /internal/runs`
> (for repeated runs and test batches, US-64/US-65/US-71) is a deferred Sprint 2
> feature and is not implemented or tested here.

### Configuration (application.yml)

| Key                                              | Default | Notes                                          |
|--------------------------------------------------|---------|------------------------------------------------|
| `app.execution.limits.max-queue-length`          | `10`    | Max concurrent runs; tune per host (US-16)     |
| `app.execution.limits.queue-retry-after-seconds` | `5`     | Sent in `Retry-After` and `error.retry_after_seconds` |

### QUEUE_FULL error shape (docs/api-contracts.md §7.1)

```http
HTTP 503 Service Unavailable
Retry-After: 5

{
  "request_id": "<uuid echoed from request>",
  "error": {
    "code":                "QUEUE_FULL",
    "message":             "Execution service is busy, try again in a few seconds.",
    "retry_after_seconds": 5
  }
}
```

> **Important (FR16 v2):** repeated runs, including those triggered by
> automated batch features, count toward the same limit and receive the same
> refusal. Never add a second gate or bypass this one.

## Docker isolation, Docker access and its risk (FR5.1, FR5.2, US-09)

### Runner interface

`RunController` talks only to the `CodeRunner` interface:

```java
ExecutionResult execute(RunSpec spec);   // never throws for a normal outcome
```

`RunSpec` carries `language`, `files` (plain file names and content), `entry` and `stdin`.
`ExecutionResult` carries stdout, stderr, exit code, time, flags and `failure_kind`
(an out-of-memory kill is `non_zero_exit` with `oom_killed: true`, never `"oom"`).

| Implementation   | When it is used                                   |
|------------------|---------------------------------------------------|
| `DockerRunner`   | Default (every profile except `stub-runner`)      |
| `FakeCodeRunner` | Only with the `stub-runner` Spring profile (tests, no Docker needed) |

### One container per run

For every run `DockerRunner` starts a brand-new container with a unique name
(`run-<uuid>`), runs the code, collects stdout, stderr and the exit code, and then
**always** stops and removes the container and deletes the run's workspace folder, also
when the run crashes, times out or is killed for memory. Nothing is reused between runs.
Each container is started with:

| Option | Meaning |
|--------|---------|
| `--network none` | no network access |
| `--user 1001:1001` | non-root user |
| `--memory`, `--pids-limit` | limits read from `app.execution.limits` (DR3) |
| `--read-only` and `--tmpfs /tmp:rw,noexec,nosuid,size=16m` | read-only root file system, small writable `/tmp` that is thrown away with the container |
| `--mount type=bind,...,target=/sandbox/code,readonly` | the run's own workspace folder, mounted read-only |

The Docker image is fixed in code (`collab-sandbox-python:0.1.0`). A run request chooses
only the language, the files, the entry file and stdin; it can never add or change a Docker
option. The wall-time limit is enforced by the runner (the container is stopped). The other
limits and the compile stage are added in US-13.

### How the service reaches Docker, and the risk

`DockerRunner` starts the `docker` command line tool as a child process. That means:

- **Local run (`./mvnw spring-boot:run`):** it uses the Docker engine of your own machine.
- **docker compose:** the service image contains `docker-cli` (see `execution-service/Dockerfile`)
  and `docker-compose.yml` mounts the host's `/var/run/docker.sock` into the
  `execution-service` container.

**Risk.** Access to the Docker socket is equivalent to root access on the host. Whoever can
make this service start an arbitrary container could mount host folders or start a privileged
container. The service therefore must be treated as a trusted component:

- Never expose the execution-service port to the public internet; only the other services
  and the client's own backend calls reach it.
- Never mount the Docker socket, the host's sensitive folders or any extra host folder into a
  **run** container, and never add `--privileged`, extra capabilities or another network mode.
- Keep the Docker options in `DockerRunner` fixed (not taken from a request).
- Never execute user code on the host, not even in tests: tests use `FakeCodeRunner`
  or the real `DockerRunner`.

Hardening options such as rootless Docker or a Docker socket proxy are not part of US-09.

### How to verify US-09

Build the image once (from the repository root), then run the isolation tests:

```bash
docker build -t collab-sandbox-python:0.1.0 execution-service/runtime-images/python
cd execution-service
./mvnw -Dtest=DockerRunnerTest,DockerRunnerIsolationTest test      # mvnw.cmd on Windows
```

`DockerRunnerIsolationTest` is skipped (not failed) when Docker or the image is missing.
It covers: a second run cannot see a file written by the first, a container is removed after
success, a crash, a timeout and an out-of-memory kill, five parallel runs use five distinct
containers and leave none behind, an outside network connection fails, and the run's
workspace folder is removed.

To check by hand, count the runner's containers before and after a run:

```bash
docker ps -a --filter "name=run-" --format '{{.Names}}' | wc -l      # before
# trigger one run through the service
docker ps -a --filter "name=run-" --format '{{.Names}}' | wc -l      # expected: same count
```

## Resource limits (DR3)

Limits are read from `src/main/resources/application.yml` under `app.execution.limits`.
They are **never hard-coded** in Java source.

| Key                      | Value       | Notes                                    |
|--------------------------|-------------|------------------------------------------|
| `wall-time-seconds`      | 5           | NFR4.1 – killed after this many seconds  |
| `memory-mb`              | 128         | NFR4.2 – container memory cap            |
| `pids-limit`             | 64          | NFR4.3 – max processes inside container  |
| `max-output-bytes`       | 1 048 576   | NFR4.4 – 1 MiB stdout+stderr cap         |
| `max-request-body-bytes` | 1 048 576   | T-06 §2 – request body cap               |
| `max-queue-length`       | 8           | FR16 – concurrent/waiting run limit      |
| `queue-retry-after-seconds` | 5        | FR16 – retry hint on 503 QUEUE_FULL      |
