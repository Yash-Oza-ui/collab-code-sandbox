# execution-service

Spring Boot service that runs user code in isolated Docker containers.

- **Port:** `8082` (T-06 section 1)
- **Health:** `GET /actuator/health`
- **Run:** `POST /v1/runs` — see [docs/api-contracts.md](../docs/api-contracts.md) sections 4, V2.8 (Decision 8) & V2.9 (Decision 9)

> **Sprint 2 / T-19 status (Jay Limbasiya & Yash Oza):**
> The run endpoint consumes the unified **RunSpec** object (Decision 8) and returns
> enriched execution results with Decision 9 fields (`runner`, `ran_at`, `visibility`,
> `saved_versions`, `failure`, `compile_time_ms`).
> Runs code through **DockerRunner** (US-09, PR #40) by default. **FakeCodeRunner** is a deterministic in-process stub that is used only when the `stub-runner` Spring profile is active.
> Gated by **RunQueueGate** (US-11) for concurrency limiting.

## Run endpoint

```
POST http://localhost:8082/v1/runs
Content-Type: application/json
```

### Request fields (T-17 V2.8 / Decision 8)

| Field        | Type          | Required | Notes                                                                   |
|--------------|---------------|----------|-------------------------------------------------------------------------|
| `request_id` | string (UUID) | Yes      | Generated by the client (UUID v4); echoed in the response.              |
| `room_id`    | string        | Yes      | Room the result is broadcast to (FR4.5).                                |
| `session_id` | string (UUID) | Yes      | Stable browser session id (UUID v4, T-06 §3.3).                         |
| `language`   | string        | Yes      | One of: `cpp`, `python`, `c`, `java`, `javascript`                      |
| `stdin`      | string        | No       | Standard input; defaults to `""` (FR4.1).                               |
| `source`     | object        | Yes      | Spec object defining files or saved snapshot to execute (Decision 8).   |

> **Legacy field:** A body containing `code` is rejected with HTTP `422 INVALID_REQUEST`.

### Supported languages so far (US-08, DR1)

The endpoint accepts the five DR1 languages: `cpp`, `python`, `c`, `java`, `javascript`.
Any other value is refused with HTTP `422 UNSUPPORTED_LANGUAGE` before anything runs.

| Language | Runs end to end today? | Notes |
|----------|------------------------|-------|
| `python` | **Yes** | Image `collab-sandbox-python:0.2.0` (T-14/US-10), run by `DockerRunner` (US-09). |
| `cpp`, `c`, `java`, `javascript` | Not yet | Accepted by the endpoint, but `DockerRunner` has no image for them. The run returns HTTP 200 with `exit_code: 2`, `failure_kind: "non_zero_exit"` and a stderr message saying the runtime currently supports Python only. The images arrive with US-14. |

A program that fails (non-zero exit, syntax error, exception) is **a result, not a server error**:
HTTP 200 with the program's stderr and exit code (FR4.2). A syntax error in Python gives
`failure_kind: "compile_error"`.

### Three source shapes

1. **Pair mode (inline source):**
   ```json
   {
     "kind": "inline",
     "files": [
       { "name": "main.py", "content": "print(\"hello\")" }
     ],
     "entry": "main.py"
   }
   ```
2. **Open mode (one runnable module):**
   ```json
   {
     "kind": "saved",
     "target": "module",
     "module_id": "mod_9Qx7mBvA2nR0"
   }
   ```
3. **Open mode (through entry file):**
   ```json
   {
     "kind": "saved",
     "target": "entry",
     "module_ids": "all"
   }
   ```
   *(or `"module_ids": ["mod_1", "mod_2"]`)*

### Room delivery & audience (FR4.5, T-06 §5, Decision 10)

After execution finishes, execution-service broadcasts the run result to sync-service:
- In **Pair mode**, broadcast with audience `{"kind":"room"}`.
- In **Open mode**, broadcast with targeted session audience `{"kind":"sessions","session_ids":[sessionId]}` (visibility `private`).

## Permission lookup (US-60, T-17 V2.11, FR41.4)

On every run request execution-service asks sync-service who the caller is and whether they may run
(`GET {SYNC_SERVICE_INTERNAL_URL}/internal/rooms/{room_id}/sessions/{session_id}` with
`X-Internal-Token`). The answer is never cached, so a change by the Host (Run taken away, Host-only
running) refuses the member's very next run with `403 RUN_NOT_ALLOWED` and `error.reason` of
`observer`, `run_revoked` or `host_only`.

- **`HttpPermissionLookupService`** is the real lookup and the default. It fails closed: no
  connection, a timeout, `401`, a `5xx` or an answer without a boolean `can_run` is
  `503 ROOM_SERVICE_UNAVAILABLE` and the code is not run. `404 ROOM_NOT_FOUND` is
  `404 ROOM_NOT_FOUND`; `404 SESSION_NOT_FOUND` is `403 RUN_NOT_ALLOWED` with reason `not_in_room`.
  It needs `SYNC_SERVICE_INTERNAL_URL` and `INTERNAL_API_TOKEN` (the same settings as the result broadcast).
- **`StubPermissionLookupService`** is an in-memory stub, used only when the `stub-permissions`
  Spring profile is active (`SPRING_PROFILES_ACTIVE=stub-permissions`). It returns `can_run: true` for every
  session that is not one of the well-known test session IDs (`OBSERVER_SESSION_ID`, `REVOKED_SESSION_ID`,
  `HOST_ONLY_SESSION_ID`, `NOT_IN_ROOM_SESSION_ID`). The unit tests and the integration stack in
  `docker-compose.yml` select it, because the older run scripts use made-up rooms and sessions. To run the
  integration stack with the real lookup: `EXECUTION_SPRING_PROFILES= bash tests/integration/up.sh`.

## US-10 execution metrics

The real Docker runner reports measurements from the trusted supervisor inside
the container; it does not use `FakeCodeRunner` values.

### Execution time measurement
- `execution_time_ms` uses Python's `time.monotonic_ns()` measured by the supervisor
  immediately before the user process is spawned until that process exits.
- It strictly measures the run stage and excludes queue waiting, Docker daemon
  interaction, container spin-up, workspace creation, and cleanup.
- Repeatability: Because container boot overhead is excluded, repeated executions
  of deterministic code produce consistent execution times within small variance margins.

### Peak memory measurement & high-water marks
- `peak_memory_mb` is read from genuine kernel high-water marks:
  1. cgroup v2: `/sys/fs/cgroup/memory.peak` (modern Docker on Linux/WSL2).
  2. cgroup v1: `/sys/fs/cgroup/memory/memory.max_usage_in_bytes` (legacy hosts).
  3. Fallback: `resource.getrusage(resource.RUSAGE_CHILDREN).ru_maxrss * 1024`
     (Linux child-process maximum resident set size across its lifetime).
- High-water mark integrity: Instantaneous counters (`memory.current` or
  `memory.usage_in_bytes`) are intentionally avoided because reading them after
  process exit misses the true peak if the program deallocated memory before termination.
  The high-water mark preserves the true maximum allocation regardless of later deallocation.

### Peak-memory scope & supervisor overhead
- **Measurement Boundary:** The cgroup high-water mark encompasses all processes
  in the container cgroup: the supervisor process (`collab-sandbox-runner`) and the
  submitted user process (plus any subprocesses spawned by user code).
- **Justification for Cgroup Scope:**
  1. *Resource Limit Alignment:* Container memory limits (`--memory=128m`) and
     kernel OOM decisions are enforced at the cgroup boundary. Measuring at the cgroup
     level accurately reports how close the workload was to triggering an OOM kill.
  2. *Multi-Process Support:* If submitted code spawns worker processes or helper
     tools, process-specific RSS (`ru_maxrss`) only reports the largest single child,
     whereas cgroup statistics accurately aggregate concurrent process memory.
  3. *Supervisor Overhead & Impact:* The supervisor is an idle Python process waiting
     on `child.wait()`. Its resident memory footprint is static and minimal (~8-12 MB).
     The reported `peak_memory_mb` therefore reflects the container's peak memory
     including this ~8-12 MB runtime baseline.
  4. *Fallback Scope:* In environments where cgroups are unavailable or when tested
     with `COLLAB_SANDBOX_FORCE_RUSAGE=1`, the fallback uses `ru_maxrss`, which isolates
     the submitted child process's peak RSS specifically (0 MB supervisor overhead).

### Failed runs and OOM handling
- Run timing and peak memory are recorded for successful runs, non-zero exits,
  syntax errors (`compile_error`), timeouts, and OOM kills.
- **OOM kills:** the supervisor raises the child's `oom_score_adj` to 1000, which biases the
  kernel's OOM victim selection toward the submitted process and away from the supervisor.
  This is a bias, not a guarantee: the kernel chooses the victim by its own scoring, so the
  supervisor could still be killed in rare cases. The supervisor cannot lower its own score
  because the container drops `CAP_SYS_RESOURCE`. When the supervisor survives, it records the
  real monotonic execution time and cgroup peak reached before the kill. If the container
  ended before the metrics file was written (for example the supervisor was killed),
  `execution_time_ms` and `peak_memory_mb` report `0.0` (unavailable) rather than a made-up
  value.
- **Timeouts:** the clock stops when the wall-time limit fires, so a timed-out run reports
  about the configured limit; the short SIGTERM-to-SIGKILL grace period is not counted.
- Python has no separate compile stage, so `compile_time_ms` remains `null`;
  `execution_time_ms` is still populated for syntax errors because the Python
  interpreter must start and parse the submitted file.

The response/UI contract is unchanged. `RunOutputPanel` already renders the
exit outcome and the time/memory metrics in a metadata row separate from
stdout/stderr; no `RunPanel.tsx` changes are needed for this story.

## How to run locally

### 1. Build the runtime image

From the repository root, build the Python runtime image using the Dockerfile maintained in this repository:

```bash
docker build -t collab-sandbox-python:0.2.0 execution-service/runtime-images/python
```

The execution service expects this image tag when running Python code. Build the image again whenever its Dockerfile changes.

### 2. Run the execution service

Make sure Docker is running and the Docker CLI is available to the service.

```bash
cd execution-service

# Run all tests
mvnw.cmd test               # Windows
./mvnw test                 # Linux / macOS

# Start the service (port 8082)
mvnw.cmd spring-boot:run    # Windows
./mvnw spring-boot:run      # Linux / macOS
```

### Execution boundary

Submitted code is executed only inside temporary Docker containers started by `DockerRunner` through the machine's Docker daemon. User code must never be executed directly on the host, including during local development or tests.

`FakeCodeRunner` is a deterministic stub for controlled development and tests; it does not execute submitted code. It is selected only when the `stub-runner` profile is explicitly enabled.

The project does not use hosted code-execution services such as Judge0 or Piston. Runtime images are built from Dockerfiles maintained under `execution-service/runtime-images/`.

## Queue gate (FR16, US-11)

When the run queue is full the service refuses the new request immediately --
no container is started, no existing run is disturbed.

### How it works

Every public run request (`POST /v1/runs`) calls the **one** `RunQueueGate`. The gate
holds a semaphore whose size is `app.execution.limits.max-queue-length`. When all
permits are in use the gate throws `QueueFullException` before invoking the
code runner. `QueueFullExceptionHandler` maps that to an HTTP 503 response.

Queue health and observable in-flight state (`in_flight`, `max_queue_length`,
`retry_after_seconds`) are exposed via Spring Boot Actuator at `GET /actuator/health`
(`QueueHealthIndicator`) for monitoring and deterministic test coordination.
The details are hidden by default (`management.endpoint.health.show-details: never`).
`docker-compose.yml` keeps them hidden too (default `never`). Only the integration harness
(`tests/integration/up.sh` and the CI `integration` job) sets `MANAGEMENT_HEALTH_SHOW_DETAILS=always`;
do not enable it in production.

> **Note on API scope:** Testing in this PR covers the public endpoint `POST /v1/runs`,
> verifying that repeated public calls count toward the same queue limit and receive
> the 503 `QUEUE_FULL` refusal. The future internal endpoint `POST /internal/runs`
> (for repeated runs and test batches, US-64/US-65/US-71) is a deferred Sprint 2
> feature and is not implemented or tested here.

### Configuration (application.yml)

| Key                                              | Default | Notes                                          |
|--------------------------------------------------|---------|------------------------------------------------|
| `app.execution.limits.max-queue-length`          | `10`    | Max concurrent runs; tune per host (US-16)     |
| `app.execution.limits.queue-retry-after-seconds` | `5`     | Sent in `Retry-After` and `error.retry_after_seconds` |

### QUEUE_FULL error shape (docs/api-contracts.md §7.1)

```http
HTTP 503 Service Unavailable
Retry-After: 5

{
  "request_id": "<uuid echoed from request>",
  "error": {
    "code":                "QUEUE_FULL",
    "message":             "Execution service is busy, try again in a few seconds.",
    "retry_after_seconds": 5
  }
}
```

> **Important (FR16 v2):** repeated runs, including those triggered by
> automated batch features via `POST /internal/runs`, count toward the same
> limit and receive the same refusal. Never add a second gate or bypass this one.

## Repeated-run budget & internal run endpoint (NFR14, CR10, US-64, T-18 Decision 7)

Features that perform multiple runs (complexity measurement, generated-test batches,
sanitizer checks) request executions through `POST /internal/runs` authenticated with
`X-Internal-Token: ${INTERNAL_API_TOKEN}`. Internal runs are **never** broadcast as
user-visible `run-result` messages.

### How it works

- Each `POST /internal/runs` request gets its own per-request `RunBudget` instance
  from `RunBudgetFactory` (never a global counter).
- Before starting the next run, `RunBudget` checks both configured limits:
  1. Runs-per-request cap (`app.execution.limits.max-runs-per-request`)
  2. Aggregate execution time budget (`app.execution.limits.aggregate-time-budget-ms`)
- Every accepted run goes through the **same** `RunQueueGate` (FR16, US-11) and the
  **same** `CodeRunner` (per-run 5 s wall-clock limit, 128 MB memory limit, container
  isolation — NFR3, NFR4).
- When either limit is reached, the next run is refused before starting a container with
  HTTP `429 Too Many Requests`, `Retry-After` header, and `RUN_BUDGET_EXCEEDED`. Any runs
  already completed before the limit was hit are preserved on the budget/exception and not lost.

### Configuration (`application.yml`, DR3)

| Key                                               | Default | Notes                                                          |
|---------------------------------------------------|---------|----------------------------------------------------------------|
| `app.execution.limits.aggregate-time-budget-ms`   | `20000` | Per-request aggregate wall-clock budget (ms, NFR14)            |
| `app.execution.limits.max-runs-per-request`       | `10`    | Maximum number of runs allowed per repeated-run request (NFR14)|
| `app.execution.limits.budget-retry-after-seconds` | `30`    | Sent in `Retry-After` and `error.retry_after_seconds` on 429   |
| `app.execution.limits.sanitizer-memory-mb`        | `512`   | Maximum memory per container for sanitizer runs (MB, DR3, DR5) |

### `RUN_BUDGET_EXCEEDED` error shape (`docs/examples/v2-error-run-budget-exceeded.json`)

```http
HTTP 429 Too Many Requests
Retry-After: 30

{
  "request_id": "<uuid echoed from request>",
  "error": {
    "code": "RUN_BUDGET_EXCEEDED",
    "message": "Aggregate repeated-run execution budget of 20000ms exceeded (NFR14).",
    "reason": "aggregate_time_budget",
    "retry_after_seconds": 30
  }
}
```

`error.reason` is `"aggregate_time_budget"` when the aggregate time budget is hit, or
`"max_runs_per_request"` when the runs-per-request cap is hit.

## Docker isolation, Docker access and its risk (FR5.1, FR5.2, US-09)

### Isolation rules (NFR3.1 to NFR3.4, US-12)

Every run happens in an ephemeral container strictly isolated from the host, other runs, and external networks.
The isolation settings are applied in a single centralized container-start function (`DockerRunner#buildIsolatedContainerProcess`),
guaranteeing that every run kind (including future test batches and sanitizer runs in US-71/US-73) reuses them and cannot skip any rule.

| :--- | :--- | :--- | :--- |

| **Non-root user** | NFR3.2 | UID/GID 1001 enforced (`sandbox` user). ### Runner interface

`RunController` talks only to the `CodeRunner` interface:

```java
ExecutionResult execute(RunSpec spec);   // never throws for a normal outcome
```

`RunSpec` carries `language`, `files` (plain file names and content), `entry` and `stdin`.
`ExecutionResult` carries stdout, stderr, exit code, time, flags and `failure_kind`
(an out-of-memory kill is `non_zero_exit` with `oom_killed: true`, never `"oom"`).

| Implementation   | When it is used                                   |
|------------------|---------------------------------------------------|
| `DockerRunner`   | Default (every profile except `stub-runner`)      |
| `FakeCodeRunner` | Only with the `stub-runner` Spring profile (tests, no Docker needed) |

### One container per run

For every run `DockerRunner` starts a brand-new container with a unique name
(`run-<uuid>`), runs the code, collects stdout, stderr and the exit code, and then
**always** stops and removes the container and deletes the run's workspace folder, also
when the run crashes, times out or is killed for memory. Nothing is reused between runs.
Each container is started with:

| Option | Meaning |
|--------|---------|
| `--network none` | no network access |
| `--user 1001:1001` | non-root user |
| `--memory`, `--pids-limit` | limits read from `app.execution.limits` (DR3) |
| `--read-only` and `--tmpfs /tmp:rw,noexec,nosuid,size=16m` | read-only root file system, small writable `/tmp` that is thrown away with the container |
| `--mount type=bind,...,target=/sandbox/code,readonly` | the run's own workspace folder, mounted read-only |

The Docker image is fixed in code (`collab-sandbox-python:0.1.0`). A run request chooses
only the language, the files, the entry file and stdin; it can never add or change a Docker
option. The wall-time limit is enforced by the runner (the container is stopped). The other
limits and the compile stage are added in US-13.

### How the service reaches Docker, and the risk

`DockerRunner` starts the `docker` command line tool as a child process. That means:

- **Local run (`./mvnw spring-boot:run`):** it uses the Docker engine of your own machine.
- **docker compose:** the service image contains `docker-cli` (see `execution-service/Dockerfile`)
  and `docker-compose.yml` mounts the host's `/var/run/docker.sock` into the
  `execution-service` container.

**Risk.** Access to the Docker socket is equivalent to root access on the host. Whoever can
make this service start an arbitrary container could mount host folders or start a privileged
container. The service therefore must be treated as a trusted component:

- Never expose the execution-service port to the public internet; only the other services
  and the client's own backend calls reach it.
- Never mount the Docker socket, the host's sensitive folders or any extra host folder into a
  **run** container, and never add `--privileged`, extra capabilities or another network mode.
- Keep the Docker options in `DockerRunner` fixed (not taken from a request).
- Never execute user code on the host, not even in tests: tests use `FakeCodeRunner`
  or the real `DockerRunner`.

Hardening options such as rootless Docker or a Docker socket proxy are not part of US-09.

### How to verify US-09

Build the image once (from the repository root), then run the isolation tests:

```bash
docker build -t collab-sandbox-python:0.2.0 execution-service/runtime-images/python
cd execution-service
./mvnw -Dtest=DockerRunnerTest,DockerRunnerIsolationTest test      # mvnw.cmd on Windows
```

`DockerRunnerIsolationTest` is skipped (not failed) when Docker or the image is missing.
It covers: a second run cannot see a file written by the first, a container is removed after
success, a crash, a timeout and an out-of-memory kill, five parallel runs use five distinct
containers and leave none behind, an outside network connection fails, and the run's
workspace folder is removed.

To check by hand, count the runner's containers before and after a run:

```bash
docker ps -a --filter "name=run-" --format '{{.Names}}' | wc -l      # before
# trigger one run through the service
docker ps -a --filter "name=run-" --format '{{.Names}}' | wc -l      # expected: same count
```

## Resource limits (DR3, US-13, NFR4.1 to NFR4.5)

Limits are read from `src/main/resources/application.yml` under `app.execution.limits`.
They are **never hard-coded** in Java source (DR3). To tune limits per host or environment, update `application.yml` or override via environment variables.

| Key                        | Initial Value | Traceability | Description / Contract Outcome                                       |
|----------------------------|---------------|--------------|----------------------------------------------------------------------|
| `wall-time-seconds`        | 5             | NFR4.1       | Maximum wall-clock time per run (and per test). On timeout: `timed_out: true`, `failure_kind: "timeout"`, `message: "Time limit exceeded"`. |
| `memory-mb`                | 128           | NFR4.2       | Container memory cap with swap disabled (`--memory-swap` = `--memory`). On OOM: `oom_killed: true`, `failure_kind: "non_zero_exit"`, `message: "Memory limit exceeded"`. |
| `pids-limit`               | 64            | NFR4.3       | Max processes/threads inside container. Fork bombs are contained within the sandbox. |
| `max-output-bytes`         | 1 048 576     | NFR4.4       | Combined stdout + stderr cap (1 MiB). When exceeded: `output_truncated: true`. |
| `compile-timeout-seconds`  | 10            | NFR4.5       | Separate compile-stage timeout for compiled languages.               |
| `max-request-body-bytes`   | 1 048 576     | T-06 §2 / DR5| Maximum size of a single run request body (1 MiB).                   |
| `max-queue-length`         | 10            | FR16 / US-11 | Max concurrent and waiting runs before refusing new runs with 503.   |
| `queue-retry-after-seconds`| 5             | FR16 / US-11 | Seconds sent in `Retry-After` header and error body on queue full.   |
| `aggregate-time-budget-ms` | 20 000        | NFR14 / US-64| Aggregate wall-clock time budget per repeated-run request (ms).      |
| `max-runs-per-request`     | 10            | NFR14 / US-64| Maximum runs allowed per repeated-run request.                       |
| `budget-retry-after-seconds`| 30           | NFR14 / US-64| Seconds sent in `Retry-After` header and error body on 429 budget hit.|

> **Per-Host Configuration (DR3 / US-16):**
> Every limit listed above is configurable per deployment host via environment variables
> (e.g. `APP_EXECUTION_LIMITS_WALL_TIME_SECONDS=3`) or custom application profile files.
> Nothing is hard-coded in Java source. Final host-specific values are recorded only after
> the deployment host is fixed and tested. See [docs/host-config.md](../docs/host-config.md) for the master DR3 limits table.
